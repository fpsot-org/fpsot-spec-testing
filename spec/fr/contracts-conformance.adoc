= Tests de contrat et suites de conformité
include::_fpsot-terms.adoc[]

Ces règles couvrent deux sortes de tests partagés dans les projets de la {abbr-fpsot-first}.
Un test de contrat vérifie une interface par rapport à son contrat publié.
Une suite de conformité vérifie qu’un composant respecte une spécification, pour qu’un autre composant puisse prendre sa place.

== Tests de contrat d’une API

[[TST-040]]
*TST-040.* Le fournisseur d’une {abbr-api-first} DOIT tester son serveur par rapport à la description publiée, selon API-020 et API-021.
Chaque réponse de ces tests DOIT respecter le schéma que la description donne pour son opération et son code d’état.
Les tests DEVRAIENT appeler chaque opération, et DEVRAIENT produire chaque code d’état que la description énumère.
Les clients se fondent sur la description publiée, donc un serveur qui s’en écarte les brise.

[[TST-041]]
*TST-041.* Un fournisseur DOIT comparer sa description avec celle de sa dernière version publiée, dans l’intégration continue.
La vérification DOIT échouer à un changement qui brise un client, au sens d’API-051.
Un changement qui vient avec une nouvelle version majeure, selon API-050, fait exception.
Un outil détecte alors un changement incompatible avant qu’un client ne le subisse.

[[TST-042]]
*TST-042.* Un consommateur et un fournisseur PEUVENT aussi employer des contrats pilotés par le consommateur.
Avec cette méthode, les tests du consommateur notent ses besoins, et le fournisseur vérifie chaque note.
Un contrat de consommateur NE DOIT PAS exiger quoi que ce soit que la description publiée ne permet pas.
Quand ils diffèrent, la description publiée l’emporte.
Les contrats de consommateur montrent quelles parties d’une {abbr-api} chaque client emploie.
La description publiée reste le contrat de tous les clients.

[[TST-043]]
*TST-043.* Un producteur DEVRAIT tester chaque événement qu’il envoie avec le schéma publié de son type, selon API-102 et API-103.
Un consommateur d’événements reçoit alors les données que le schéma promet.

== Suites de conformité

[[TST-044]]
*TST-044.* Chaque spécification de {abbr-fpsot} PEUT fournir une suite de conformité.
Une suite de conformité DOIT employer seulement les interfaces publiques d’un composant, comme une {abbr-api} ou des fichiers.
Elle NE DOIT PAS exiger un langage, un cadre d’application ou un exécuteur donné dans le composant qu’elle teste.
Toute mise en œuvre, dans tout langage, peut alors exécuter la même suite.

[[TST-045]]
*TST-045.* Un composant qui en remplace un autre DOIT réussir la même suite de conformité que le composant qu’il remplace.
Un composant qui remplace une règle d’affaires DOIT réussir les scénarios de cette règle, sauf ceux qu’il change exprès.
Il DOIT énumérer les scénarios qu’il change, avec leurs étiquettes, et donner un nouveau scénario pour chaque comportement changé.
Les institutions peuvent alors remplacer un composant ou une règle, et savoir ce qui tient toujours.

[[TST-046]]
*TST-046.* Chaque version d’une suite de conformité DOIT nommer la version de la spécification qu’elle teste.
Ses numéros majeur et mineur DOIVENT être ceux de cette version.
Chaque test DOIT citer les identifiants des exigences qu’il vérifie.
Un résultat peut alors dire quelles règles un composant respecte, et pour quelle version.

[[TST-047]]
*TST-047.* Un résultat de suite NE DOIT PAS être présenté comme une certification, une approbation ou un appui de {abbr-fpsot}.
Une entreprise PEUT déclarer qu’un produit réussit une version donnée d’une suite, avec la date et tous les résultats.
Une suite vérifie les comportements qu’elle couvre, et non la qualité, la sécurité ou le soutien d’un produit.
Les organismes acheteurs doivent toujours les évaluer.

[[TST-048]]
*TST-048.* Une suite de conformité DEVRAIT écrire ses résultats sous une forme qu’une machine peut lire.
Les résultats DEVRAIENT donner chaque identifiant d’exigence avec son issue : réussi, échoué ou sans objet.
Un organisme acheteur peut alors comparer les résultats de plusieurs produits, règle par règle.

== Comparaison avec GovStack

GovStack vérifie aussi les produits par rapport à ses spécifications, avec des tests de leur {abbr-api} et une autoévaluation.
Ses link:https://govstack.global/software/how-is-compliance-measured/[niveaux de conformité] classent un produit selon la part des exigences qu’il respecte.
Un produit qui atteint un niveau peut entrer au catalogue de GovStack.
Pour sa part, {abbr-fpsot} ne classe rien et ne répertorie aucun produit.
Un résultat nomme la version de la suite et l’issue de chaque exigence, selon TST-046 à TST-048.
