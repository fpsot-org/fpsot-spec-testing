= Niveaux de test
include::_fpsot-terms.adoc[]

Ces règles définissent les niveaux de test d’un projet de la {abbr-fpsot-first}.
Elles disent ce que vérifie chaque niveau, ce qu’il peut remplacer par une {term-test-double}, et comment équilibrer les niveaux.

== Niveaux et leur but

Chaque niveau ci-dessous a une seule définition.
Les noms gardent le sens du link:https://glossary.istqb.org/[glossaire de l’ISTQB], en résumé.
Le glossaire range le test de bout en bout et le test fonctionnel parmi les types de test.
Cette spécification en fait des niveaux, parce que chacun s’exécute comme un groupe distinct dans l’intégration continue.

Test unitaire::
Test de la plus petite partie du code qui peut s’exécuter seule.
Par exemple, une fonction ou une classe.
Il vérifie que cette partie se comporte comme prévu, à l’écart du reste.

Test d’intégration::
Test de la façon dont une partie du code fonctionne avec une dépendance réelle.
Par exemple, une base de données, un courtier de messages ou un autre composant.
Il vérifie les interactions qu’un test unitaire remplace par une {term-test-double}.

Test de contrat::
Test qui vérifie qu’un fournisseur et un consommateur emploient une interface comme le dit son contrat publié.
Le glossaire le traite comme une sorte de test d’intégration.
Cette spécification en fait un niveau distinct, parce qu’il vérifie un document publié, et non une seule paire de composants.

Test fonctionnel::
Test d’un comportement de tout le produit, tel qu’un ou une spécialiste du domaine le décrit.
Son scénario dit ce que le produit doit faire.
Son résultat aide l’organisme propriétaire à décider s’il accepte le produit.
Le glossaire appelle ce but le test d’acceptation.

Test de bout en bout::
Test d’un processus d’affaires complet, du début à la fin.
Il traverse le produit et les systèmes qui l’entourent.
Il s’exécute dans un environnement qui ressemble à la production.

[[TST-001]]
*TST-001.* Chaque test du comportement d’un projet DOIT appartenir à un niveau de cette page.
Le projet DOIT marquer le niveau de chaque test, par exemple par un dossier ou une étiquette.
Les tests de charge, de performance et de migration, selon TST-052, sont hors des cinq niveaux.
Les vérifications d’accessibilité, selon TST-066, le sont aussi.
L’intégration continue peut alors exécuter chaque niveau comme une vérification distincte, selon TST-060.
Le lectorat sait aussi ce que prouve un test qui échoue, et ce qu’il ne prouve pas.

== Doublures de test

Une {term-test-double} remplace une dépendance réelle pendant un test.
Elle peut renvoyer des réponses fixes, noter les appels qu’elle reçoit ou contenir une version simple de la dépendance.

[[TST-002]]
*TST-002.* Un test NE DOIT PAS remplacer par une {term-test-double} ce que ce tableau fait exécuter réellement à son niveau.
Un test PEUT remplacer ce que le tableau permet.
Un test de bout en bout qui remplace un système externe DOIT nommer ce système dans son rapport de test.
Chaque niveau ne prouve quelque chose que s’il exécute les parties dont cette preuve a besoin.

[cols="1,2,2",options="header"]
|===
|Niveau |S’exécute réellement |Peut employer une doublure de test pour
|Test unitaire |Le code de l’unité. |Chaque dépendance hors de l’unité, comme une base de données, une horloge ou une autre classe.
|Test d’intégration |Le code et chaque dépendance que nomme le test, comme le produit de base de données. |Les autres dépendances, que le test ne nomme pas.
|Test de contrat |Le code du fournisseur qui sert l’interface, ou le code du consommateur qui l’appelle. |L’autre côté du contrat, construit à partir du contrat publié.
|Test fonctionnel |Le produit tel que construit, par ses interfaces publiques. |Les systèmes externes que le produit ne possède pas, comme un service de paiement.
|Test de bout en bout |Le produit et les systèmes du processus, tels que déployés. |Seulement un système externe qui n’offre aucun environnement de test.
|===

[[TST-003]]
*TST-003.* Une équipe DEVRAIT vérifier chaque comportement au plus bas niveau qui peut en détecter les défauts.
La plupart des tests d’un projet DEVRAIENT alors être unitaires, et les tests de bout en bout, les moins nombreux.
Un niveau plus haut DEVRAIT vérifier seulement ce qu’un niveau plus bas ne peut pas vérifier.
Un exemple est le travail de plusieurs parties ensemble.
Les tests de bas niveau sont rapides et pointent le défaut exact.
Les tests de haut niveau sont lents, et un échec peut y venir de bien des endroits.

== Tests reproductibles

[[TST-004]]
*TST-004.* Un test DOIT donner le même résultat à chaque exécution du même code.
Il NE DOIT PAS dépendre de l’ordre des tests, d’un autre test ou de la machine qui l’exécute.
Il NE DOIT PAS attendre un temps fixe pour laisser une chose se produire.
Il DOIT plutôt attendre une condition, avec un délai maximal.
Un test dont le résultat change sans changement du code ne peut rien prouver.

== Règles d’affaires

Dans un produit de {abbr-fpsot}, une règle d’affaires est du code ordinaire qu’une institution peut remplacer.
Aucun moteur de règles n’est exigé.

[[TST-005]]
*TST-005.* Le test d’une règle d’affaires DOIT vérifier la règle par son interface, avec des entrées et des résultats attendus.
Il NE DOIT PAS dépendre de la façon de bâtir la règle, en code ordinaire ou par un moteur.
Le même test vérifie alors la règle par défaut et toute règle qu’une institution met à sa place.
TST-045 fixe ce que doit réussir une telle règle de remplacement.

== Outils

[[TST-006]]
*TST-006.* Un projet PEUT respecter ces règles avec n’importe quel langage, exécuteur de tests et cadre d’application.
Un projet DEVRAIT nommer dans son dépôt les outils et les versions qu’il emploie pour chaque niveau.
Chaque projet choisit alors les outils de son langage, et les personnes qui contribuent les trouvent au même endroit.
La future spécification de {abbr-fpsot} sur le code fixera les choix propres à chaque langage.
