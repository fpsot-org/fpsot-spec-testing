= Fichiers de fonctionnalité en français et en anglais
include::_fpsot-terms.adoc[]

Ces règles fixent comment un projet de la {abbr-fpsot-first} garde chaque fichier de fonctionnalité en français et en anglais.
Les deux versions sont des tests, et les deux s’exécutent.

== Deux versions de chaque fonctionnalité

[[TST-030]]
*TST-030.* Chaque fichier de fonctionnalité DOIT exister en français et en anglais.
Les deux versions DOIVENT avoir le même nom de fichier, dans un dossier par langue, comme `features/en/` et `features/fr/`.
Le nom de fichier DOIT être en anglais et en kebab-case, comme `record-a-person.feature`.
Cette exigence suit NAM-072 de la spécification sur le nommage.
Les spécialistes du domaine au Québec et au Canada peuvent alors lire et approuver les scénarios dans leur langue.

== Mots clés

link:https://cucumber.io/docs/gherkin/reference/[Gherkin] définit ses mots clés pour chaque langue dans le fichier link:https://github.com/cucumber/gherkin/blob/33693f4b5a76bb86dee61d0b287d6f2c700813e4/gherkin-languages.json[gherkin-languages.json].
Pour le français, ce fichier offre plusieurs mots clés pour la plupart des éléments.

[[TST-031]]
*TST-031.* La première ligne de chaque fichier de fonctionnalité DOIT être exactement `# language: fr` ou `# language: en`.
Le fichier DOIT employer seulement les mots clés de ce tableau, qui viennent des dialectes officiels de Gherkin.
La version anglaise déclare aussi sa langue, même si Gherkin lit l’anglais par défaut.
Un seul mot clé par élément permet de comparer facilement les deux versions, ligne par ligne.
Ce tableau prend `Scénario` plutôt qu’`Exemple`, parce qu’`Exemples` nomme déjà le tableau d’un Plan du scénario.

[cols="1,1",options="header"]
|===
|Anglais |Français
|`Feature` |`Fonctionnalité`
|`Background` |`Contexte`
|`Rule` |`Règle`
|`Scenario` |`Scénario`
|`Scenario Outline` |`Plan du scénario`
|`Examples` |`Exemples`
|`Given` |`Étant donné`
|`When` |`Quand`
|`Then` |`Alors`
|`And` |`Et`
|`But` |`Mais`
|===

== Parité

[[TST-032]]
*TST-032.* Les versions française et anglaise d’un fichier de fonctionnalité DOIVENT avoir la même structure.
Elles DOIVENT avoir les mêmes règles, scénarios et exemples, dans le même ordre, avec les mêmes étiquettes.
Chaque scénario DOIT avoir le même nombre d’étapes, avec des mots clés de la même colonne du tableau de TST-031.
Les cellules des tableaux, les lignes des tableaux Exemples et les valeurs entre guillemets des étapes DOIVENT être les mêmes.
Seuls diffèrent les mots clés, les noms, les descriptions des fonctionnalités et règles, le reste des étapes et les en-têtes.
Les deux versions vérifient alors les mêmes comportements avec les mêmes données.

[[TST-033]]
*TST-033.* Une traductrice ou un traducteur NE DOIT PAS traduire les données de test d’un fichier de fonctionnalité.
Un nom, un code, une adresse ou un identifiant est une donnée, avec la même valeur dans les deux versions.
Un changement à une version DOIT changer l’autre dans la même demande de fusion.
Le texte français DOIT suivre l’usage de l’Office québécois de la langue française, selon WRT-031.
La version française NE DOIT PAS être une traduction automatique brute, selon WRT-033.
Une valeur traduite testerait un autre cas, et une version laissée en arrière testerait un autre comportement.

[[TST-034]]
*TST-034.* L’intégration continue DOIT analyser chaque fichier de fonctionnalité avec un analyseur officiel de Gherkin.
Un analyseur officiel est une mise en œuvre du projet link:https://github.com/cucumber/gherkin/blob/33693f4b5a76bb86dee61d0b287d6f2c700813e4/README.md[cucumber/gherkin], comme `gherkin-official` pour Python.
L’intégration continue DOIT échouer à une erreur d’analyse, ou quand un fichier enfreint TST-031, TST-032 ou TST-036.
Un mot clé mal écrit peut changer une étape en texte simple, que seules ces vérifications révèlent.
Les tests de la vérification elle-même DEVRAIENT comprendre des fichiers brisés qu’elle doit rejeter.
La tâche `gherkin` de ce {term-repository} en est un exemple : `examples/check-features.py`, avec ses tests dans `examples/test-features.sh`.

[[TST-035]]
*TST-035.* L’intégration continue DOIT exécuter les deux versions de chaque fichier de fonctionnalité sur le produit.
Les définitions d’étapes des deux langues DOIVENT appeler le même code.
Une version qui ne s’exécute pas peut se briser sans que personne le remarque.

[[TST-036]]
*TST-036.* Un scénario, un Plan du scénario et un Contexte NE DOIVENT PAS avoir de description.
Leur nom dit ce qu’ils vérifient, selon TST-022.
L’analyseur lit une étape au mot clé mal écrit comme une description, et la vérification de TST-034 les rejette.

== Exemple

La fonctionnalité `examples/features/fr/record-a-person.feature` et sa version anglaise montrent ces règles.
Elles décrivent des règles du modèle Party de la spécification sur les modèles de données, DMO-032 et DMO-034.
Elles emploient des données synthétiques, selon TST-050 à TST-056.
Dans les deux langues, une valeur dans une étape se place entre des guillemets droits doubles.
Beaucoup d’outils d’étapes lisent une valeur sous cette forme, et les deux versions gardent ainsi les mêmes données.
